# core-commands commit steps not respected during plan execution



## Summary

When executing an implementation plan, the commit step (described in `supervised-plan-execution` and delegated to `core-commands`) is performed as a single inlined shell one-liner instead of following the mandatory mktemp → Write tool → describe → rm → jj new sequence.

## Observed behavior

```
TMP=$(mktemp); printf '%s\n' 'feat(naming): add flat_path_for helper' 'Derives flat normalized MP3 name from source parent dir hash so every normalized file lives directly under normalized_dir.' > "$TMP"; jj describe --stdin < "$TMP" && rm "$TMP" && jj new
```

## Expected behavior

Per `core-commands` (Temp File Pattern), the sequence must be:

1. `mktemp` via Bash tool → returns a path
2. Read tool → check existing content (if any)
3. Write tool → write the commit message to that path
4. Bash tool → `jj describe --stdin < "$TMPFILE"`
5. Bash tool → `rm "$TMPFILE"`
6. Bash tool → `jj new`

The Write tool must produce the file; the shell must never generate multi-line content itself.

## Root cause analysis

### RC1: The anchor command is shown without its binding steps

`supervised-plan-execution` step 6 (both at "Execute Tasks" and "Commit After Each Task") displays:

```
jj describe --stdin < "$TMPFILE" && rm "$TMPFILE" && jj new
```

but only *names* the preceding steps ("use the temp file pattern from `core-commands`"). The agent sees a runnable one-liner whose only missing piece is `$TMPFILE`, and fills the gap itself with `TMP=$(mktemp); printf ... > "$TMP"`. The pattern that must be followed lives in a different skill the agent has no reason to load at commit time.

Contribution: high. This is the direct mechanical cause.

### RC2: `printf` is a loophole the rules do not catch

`core-commands` says "NEVER use heredocs (`cat <<'EOF'`) or `echo` for multi-line content." `printf '%s\n' ...` is neither heredoc nor echo, so the agent can comply with the literal prohibition while still inlining multi-line content and skipping the Write tool. A prohibition list with an unlisted sibling always gets bypassed by the sibling.

Contribution: medium-high. Enables rationalization-by-compliance.

### RC3: Failure type misdiagnosed → wrong form of guidance

Per the writing-skills "Match the Form to the Failure" matrix, this failure is **"complies, but output has the wrong shape"** (the commit happens, but skips required elements). The correct fix form is a **positive recipe** stating the exact sequence of tool calls. The current guidance is a prohibition ("NEVER use heredocs or echo") plus a prose cross-reference, which is the wrong form for this failure and invites negotiation.

Contribution: medium. Form mismatch makes the existing rules easy to bypass even when loaded.

### RC4: Competing instruction sources at commit time

The runtime's own system guidance favors heredoc-style one-shot commit blocks; `caveman-commit` only produces the message (it explicitly "does not commit"). So at commit time the agent holds: a message (from caveman-commit), a one-liner (from the plan/skill), and no enforceable pointer to the full multi-tool protocol. The conflicting defaults win because the normative pattern is one skill away, not in view.

Contribution: low-medium. Amplifier, not primary cause.

## Proposed approach

Follow the TDD-for-skills cycle (writing-skills): baseline → minimal fix → re-test.

1. **RED (baseline already exists):** the observed one-liner is the documented baseline failure. Capture variants by running plan-execution pressure scenarios in fresh sessions and recording every way agents inline content (printf, echo, heredoc, `tee`, `<<<`, command substitution).

2. **GREEN (minimal fix), matching the correct form:**

   - In `supervised-plan-execution`, replace the bare command with the **full positive recipe**, in place, at every occurrence of the commit step. Not a cross-reference — the sequence of tool calls, written as the recipe the agent must emit:

     ```
     Bash tool:  mktemp                      → note the returned path
     Write tool: <caveman-commit message>    → to the returned path
     Bash tool:  jj describe --stdin < "<path>"
     Bash tool:  rm "<path>" && jj new
     ```

   - In `core-commands`, close the printf loophole by replacing the shape-based prohibition with an **observable-predicate rule**: any path passed to `--stdin`, `-F`, `--option`, etc. must have been produced by the Write tool in this session. Inlining multi-line content via heredoc, echo, printf, tee, `<<<`, or command substitution is out regardless of the tool used — not "more prohibited verbs," one condition the agent can self-check ("did the Write tool write this file?").

3. **REFACTOR (close loopholes from re-tests):** each new evasion variant becomes an explicit counter in the recipe; keep the rationalization table in `core-commands` updated from test iterations.

4. **Micro-test wording** (fresh-context reps, no-guidance control, 5+ reps, read matches manually) before full plan-execution pressure scenarios; only extend to full scenarios for the final gate.

## Acceptance criteria

- Fresh-session plan-execution runs produce commits via mktemp + Write tool, never shell-generated multi-line content.
- The commit step recipe appears complete (all 4 tool-call steps) wherever it is referenced, not as a bare `$TMPFILE` one-liner.
- `core-commands` rule is stated as a single observable predicate with no exemption clauses.
- Baseline variants (printf, echo, heredoc, tee) all blocked in re-test.
