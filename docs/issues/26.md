# writing-plans should size-check plans and split large ones into multi-plan batches

Source: brainstorm notes (2026-10-03)

## Problem

`writing-plans` (from obra/superpowers, mirrored at `skills/writing-plans/`) is a demanding skill: whenever the user asks for a plan, it attempts to write one giant `docs/plans/<DATETIME>_<PLAN_NAME>.md` right away. For complex requests this produces oversized, hard-to-execute plans.

## Desired behavior

When a plan request comes in, evaluate plan complexity **before** writing:

1. **Size check**: if the plan would stay relatively small and manageable → current single-file behavior.
2. **Split**: otherwise, engage the user to split into multiple plans.
3. Instead of one file, create a directory:
   - `docs/plans/<DATETIME>_<PLANSEQ_TITLE>/`
   - populate it with `index.md` first (reviewed by the user). The index presents each sub-plan and the recommended execution order.
4. Each sub-plan is written (possibly by a sub-agent) into `<SUBPLANS_DIR>/`.

## Open questions / unknowns

- [ ] Splitting criteria: what counts as "too complex"? (task count? file-count blast radius? estimated execution duration? number of dependencies?) Need a concrete threshold or heuristic, not vibes.
- [ ] Naming convention: what exactly is `<PLANSEQ_TITLE>` — e.g. `01_auth`, `02_payments`? Confirm format so `index.md` can link deterministically.
- [ ] Does the skill name a referenced/required skill reference like other plans do (e.g. "REQUIRED SUB-SKILL: superpowers:executing-plans")?
- [ ] Attribution: reference skill as **obra/superpowers**, not a local `~/dev/superpowers` path.
- [ ] Do we (a) patch the local `writing-plans` SKILL.md in place, or (b) create a new wrapper skill that layers the sizing/splitting pass on top of writing-plans?
- [ ] New-skill naming (if route (b)): candidates gathered so far:
  1. plan-sizer
  2. plan-splitter
  3. sizing-gate
  4. plan-triage
  5. plan-batching
  6. rightsize-plans
  7. plan-scope
  8. decompose-plan
  9. plan-first-pass
  10. plannable
- [ ] Sub-agent authoring flow: when a sub-agent writes each sub-plan, what context does it receive (index excerpt only? full user intent?) and who reviews it — the orchestrating agent or the user?
- [ ] What happens to an already-written single-file plan that turns out oversized mid-write: checkpoint and split, or restart as directory?

## Acceptance criteria

- Writing-plans (or its wrapper) contains an explicit complexity-evaluation gate before producing any plan file.
- Large requests produce `docs/plans/<DATETIME>_<PLANSEQ_TITLE>/index.md` + sub-plan files, with user review of the index before sub-plan generation.
- Skill references upstream as obra/superpowers.
- Behavior verified against a deliberately oversized test request.
